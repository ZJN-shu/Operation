# IT 运营门户（本地版）

公司运营网站的本地复刻：**FastAPI（Python） + MySQL + 单页 HTML/JS**，标签用 emoji 表示。
在原项目基础上做了简化：去掉了 Dash 平台 SQL 代理 / 网关 Token / OSS，改为直连本机 MySQL，并用
**pymysql 真参数化** + **积分账户表 + 事务**修掉了原项目「手写 SQL 插值注入」和「兑换无事务」两个硬伤。

## 功能

**用户端**
- 🔐 登录（管理员 / 普通用户两种角色）
- 🖼️ 首页活动轮播图（自动轮播）+ 最新公告 + 热门课程
- ⭐ 积分显示（顶栏常驻）+ 积分流水 + 我的兑换
- 📚 课程中心（报名 / 完成得积分）
- 🎁 礼品商城（积分兑换，事务扣库存 + 扣积分，防超发）
- 🎪 活动公告（参与活动 / 阅读公告得积分，幂等）
- 🔍 全局搜索框（走倒排索引：多词交集召回 + 字段加权排序，见下文）

**管理后台**（管理员可一键在用户端 / 后台之间切换）
- 📊 数据看板（用户数、DAU、发放/消耗积分、待发货订单、近 7 天积分趋势、热门礼品、最近订单）
- 📚 课程管理（新增 / 编辑文案 / 上架 / 下架）
- 🎪 活动管理（新增 / 编辑 / 上架 / 下架 / **轮播图顺序管理**）
- 🎁 积分兑换（礼品新增 / 编辑积分 / 上架 / 下架）
- 🚚 订单发货（待发货 → 填写物流单号，状态与用户端「我的兑换」联动）
- 📊 数据看板内置两个 tab：**📊 总览**（指标卡 / 转化漏斗 / 履约 / 热搜 / 热度榜 / 最近订单）
  与 **💰 积分**（近 7 天积分趋势 + **全员流水实时推送** + 人工发放/扣减 + 回滚单条流水 +
  单用户余额校平 + 热门礼品兑换/库存）。积分明细不是一个独立菜单页 ——
  它和指标卡讲的是同一件事（积分发出去、花在哪），只是粒度不同（汇总 vs 逐笔）

## 埋点与指标口径（可追问的三件事）

**① 上报失败丢数怎么办？** 前端不直接发埋点，先进 `localStorage` 队列
（`static/app.js` 的 `track()`），每 5s 或页面隐藏时批量 `POST /api/analytics/events`；
**只有服务端确认收到才出队**，失败原样留着下次重投。队列封顶 300，溢出丢最旧的并补一条
`track_dropped` 事件 —— 丢数必须能在看板上被看见，不能静默消失。
（不用 `sendBeacon`：它带不上 `Authorization` 头。）

**② 重复上报怎么去重？** 每条事件带客户端生成的 `event_id`，`user_access_logs.event_id`
上有唯一约束 `uk_event`，重投命中唯一键即被数据库拒掉，`ON DUPLICATE KEY UPDATE id=id`
让 rowcount 返回 0，据此把这次算成「已收过」而不是新事件。实测：同一批事件连续重投 3 次，
`accepted` 分别是 2 / 0 / 0，库里每条 `event_id` 始终 1 行。

**③ 口径怎么定义不歧义？** 口径全部收在 `backend/metrics.py`（单一事实来源），
看板不允许自己写聚合 SQL。三条全局约定写在文件头：时间统一用服务端 `accessed_at`
（客户端 `client_time` 只做时钟偏移诊断，否则改本机时间就能刷指标）；人数类指标统一
`COUNT(DISTINCT emp_id)` 去重；空分母一律返回 `0.0`。
`GET /api/admin/metrics-defs` 把口径说明书直接吐给前端做 tooltip。

顺带补了库结构迁移：`db._migrate()` 幂等给老库补列（先加列 → 回填历史行 → 再加唯一键），
启动时自动执行。

## 积分明细：实时推送 + 人工操作（可追问的六件事）

看板上那张「近 7 天积分趋势」是**按天聚合**的，回答不了「谁、几点、因为什么、加了几分」。
所以看板顶栏分了两个 tab，**积分 tab** 补齐的是**明细**粒度：全员流水可筛可分页，新流水主动推给
每一个开着「有看板权限」的管理端（不用手动刷新），并且管理员能在这里发放 / 扣减 / 回滚 / 校平。
它和总览页共用同一个 `/api/admin/dashboard` 载荷画趋势图与礼品卡（礼品的库存和门槛分就带在
`top_gifts` 里 —— `/api/admin/gifts` 挂在 `GIFT_ADMINS` 上，`viewer` 和 `content_admin` 都读不到，
积分 tab 不能靠二次请求补库存）。

**① 为什么是「轮询 + SSE」而不是 WebSocket？**
推送源是 `point_records` 本身，它天然是一张 **transactional outbox**：未提交的行在 InnoDB
隔离下对其他连接**根本不可见**，所以「只有提交成功才推送」由数据库保证，而不是由我自己的
缓冲区保证。这条性质很重要 —— 回滚掉的事务推不出去，而且这个结论是关于 MySQL 可见性的
**真实性断言**，不是关于我记账逻辑的断言（自己维护事件缓冲的话，缓冲区漏清一次就会把
一笔不存在的加分推给管理端，比不推送更糟）。代价是 ≤400ms 延迟（`events.py` 每 0.4s 扫一次
增量），换来的是 `db.run_tx` / `logic.add_points` 这两个撑着全项目正确性的文件**一行都不用改**。

传输选 SSE 而不是 WebSocket：单向推送用不上双工；浏览器端用 `fetch` + `res.body.getReader()`
手撸帧解析，**不用 `EventSource`** —— 它不能带 `Authorization` 头，和当初否掉 `sendBeacon`
是同一条理由（见上文埋点）。

**② 提交顺序不等于 id 顺序，增量会漏。** 事务 A 拿 `id=101`、B 拿 `102`，B 先提交；此刻扫到
的最大 id 是 102，水位推到 102，等 101 提交时它已经在水位之下，**永远收不到**。所以每轮
回退 50 个 id 重扫（`_TRAILING_WINDOW`）+ 一个 500 长的去重环。边界写清楚：某个长事务攥着
id 迟迟不提交、期间提交并扫过的 id 超过 50 个，它仍会被漏掉；要彻底解决得用 binlog / CDC。

**③ 队列满了怎么办？** 每条连接一个 `maxsize=100` 的队列，满了丢最旧的一条并补一个
`dropped` 帧，前端收到就重拉当前页补齐 —— 沿用「丢数必须能被观测到，不能静默消失」那条
原则（同 `track_dropped`）。**收到普通帧绝不重拉列表**，就地把行插进表格：否则一阵流水
就是一轮请求风暴，正是前端回归测试里专门防的那类 bug。同一屏上的趋势图不重拉整个看板，
只防抖地刷自己那一块（见下文测试 ⑨）—— 明细是逐笔、趋势是按天聚合，两者的刷新节奏本来就不同。

**④ 心跳兼作鉴权。** 会话是进程内字典（`auth._SESSIONS`），没有 TTL，`drop_session` 只在
登出时调；`require_admin` 只在建流那一刻校验过一次。所以 15s 的心跳里重新 `resolve_session`，
会话没了就发 `event: bye` 并断开 —— 否则**已登出的 token 还能继续收到全量流水**。
（前端登出 / 切走 / 关页面时也会主动 abort，双保险。）

**⑤ 人工操作怎么发号？** `point_records` 上有唯一约束 `uk_ref (emp_id, ref_type, ref_id)`，
照搬「手动发放就写 `ref_id=0`」的话，同一用户**第二笔发放直接撞 1062 发不出去**。所以先有
一张发号表 `point_ops`：先插 `point_ops` 拿自增 id，再把它当 `ref_id` 写流水。
两套幂等键分工明确 —— `point_ops.uk_idem(request_id)` 挡「同一个请求被重投」（表单打开时
生成一次、整个生命周期复用，双击提交只会入账一次，第二次回 409）；`uk_ref` 挡「同一次
业务动作被重复触发」。

`ref_type` / `ref_id` 的语义约定（写在 `schema.sql` 里）：系统流水（`welcome/course/activity/
announcement/redeem`）的 `ref_id` 是业务对象 id；人工流水（`grant/deduct/revert`）的 `ref_id`
是 `point_ops.id`。**所以每一处 join `point_ops` 都必须带 `ref_type` 限定** —— 课程流水的
`ref_id=3` 会撞上 `point_ops.id=3`，把一个不相干的管理员显示成「操作人」（看着合理、实际全错）。
回滚行的 `ref_id` 同样指向 `point_ops`（不是被回滚的流水 id），否则**查不出是谁点的回滚**；
防重复回滚交给 `point_ops.uk_reverted(reverted_record_id)` 唯一键 —— 撞 1062 而不是
「先查再插」，没有竞态窗口。

**⑥ 口径怎么处理回滚？** 回滚是纠偏，不是业务上的发放或消耗，所以 `metrics.py` 里把回滚行
（`ref_type='revert'`）和被回滚掉的**原笔**一起排除。只做前者会得到一个更隐蔽的错：
回滚一笔 `+80` 之后，发放总额纹丝不动、消耗也纹丝不动，账面上那笔钱像从没被收回过。
用**黑名单**而不是白名单，是因为白名单一旦漏掉某个既有 `ref_type`，看板上的历史数字会当场
变掉（黑名单 + 空集子查询保证加这个功能前后数字一字不差）。排除原笔用 `NOT EXISTS` 而不是
`NOT IN`：`NOT IN` 碰到子查询里的 NULL 会让整个比较变成 UNKNOWN，一行都匹配不上，
发放额会静默变成 0。

### 能力边界（被问到要主动说）

- **只覆盖一个进程。** 订阅者注册表在内存里，只能触达同一个 uvicorn worker；多 worker /
  多实例要换 Redis pub/sub 这类跨进程通道 —— 和 `auth._SESSIONS` 是同一类限制。
- **回滚兑换只退积分、不退库存**，并且打破了 `redemptions` 与积分流水的 1:1（兑换漏斗口径
  假设了这一点）。要退库存得做逆向入库 + 库存流水，当前没做。
- **余额非负是全站假设**（`redeem` 就按这个前提判够不够扣）：扣减 / 回滚后余额会为负时一律
  拒绝（400），而不是先扣成负数再让下游去兜。
- **校平只改余额缓存，不补发积分。** 口径是「`point_records` 是账本、`point_accounts.balance`
  是它的一层物化缓存」，所以校平 = 用账本重建缓存。它**不产生积分流水**（留痕在 `point_ops`
  与审计日志）—— 因为往流水里插一行**根本改不了差额**：`add_points` 同时动两边，
  `balance - SUM(ledger)` 是个不变量。如果某账户还欠着一笔该发的分，必须先用「发放」补上
  再校平，否则那笔加分永久丢失（前端在这条路径上有明确提示）。

## 搜索：倒排索引（`backend/search_index.py`）

原来 `/api/search` 是 `LIKE '%关键词%'`，两个问题：**用不上索引**（前置通配符必然全表扫），
而且关键词直接进 LIKE 模式串（`%` `_` 要转义，漏一个就是通配符注入）。现在换成倒排索引：

- **索引表 `search_keywords(keyword, doc_type, doc_id, weight)`**，唯一键 `uk_kw_doc` +
  查询索引 `idx_kw(keyword, doc_type)`，`keyword IN (...)` 走索引，不需要扫描正文。
- **分词（索引和查询共用同一个 `tokenize()`，两边同源）**：
  中文按**单字**切（不引入词典，`马克杯` → 马/克/杯）；英文数字按连续串整体成词，**同时**拆出
  字母段和数字段（`vue3` → `vue3`/`vue`/`3`），这样「搜 vue3」和「搜 vue」都能命中 ——
  老版本两边不同源的坑就在这里；停用词表过滤 `的/了/the/a` 这类词。
- **多词是交集不是并集**：`HAVING COUNT(DISTINCT keyword) = 关键词个数`，只命中一半关键词的
  文档不召回。
- **字段加权排序**：标题 3 > 分类 2 > 描述 1，同一个词在多处命中取最高权重，不稀释。
- **索引跟写操作走**：管理员上架/改标题/下架后立刻 `reindex_doc()`（下架的文档直接从索引摘掉，
  搜不到）；启动时 `rebuild_all()` 全量重建兜底；`POST /api/admin/search/reindex` 可手工重建。

**能力边界（被问到要主动说）**：没有词典就没有子词切分 —— `ZZTESTVue3` 这种粘在一起的
字母数字串拆不出 `vue`；真实场景要上 ES 的 IK / 词干化来补。本方案是「能用上索引 + 不引入
额外中间件」的取舍，不是要替代搜索引擎。

### 跑测试

```bash
# 在 运营门户 目录下（portal 的上一级）
python -m unittest discover -s portal/tests -v
```

49 个用例（`test_search.py` 22 + `test_points.py` 27），分两层：`tokenize` / `build_rows`
是纯函数，不碰数据库；召回、排序、下架摘除、以及积分那批（发放 / 幂等重放 / 回滚 / 校平 /
实时推送）跑真实 MySQL，连不上直接整体 skip，**不假装通过**。
（用标准库 `unittest` 是为了零新增依赖；也因为项目没装 `httpx`，`starlette.testclient`
导入即抛，所以积分那批是**直接调路由函数**并断言 `HTTPException` 的状态码，而不是走 HTTP。）

`test_points.py` 里最该看的两条：

- **`test_回滚的事务推不出去而已提交的推得出去`**：同一个连接里 `add_points` 之后抛异常回滚，
  断言订阅队列在 4 个轮询周期后仍然是空的，并且配一条已提交的正向对照（否则测试可能在空转）。
  这条测的是 MySQL 的可见性语义，不是我的缓冲区记账。
- **`test_校平把歪掉的余额拉回流水合计`**：先断言**流水合计一字未动**、余额被重建 —— 这条
  最先抓出了校平第一版的根本性错误（想靠插入差额流水抹平差额，结果两者同进同退，差额不变）。

前端行为回归测试（零依赖，只需 node）：把 `static/app.js` 装进假 DOM 里跑，
断言那些「点一下才知道」的行为。

```bash
node portal/tests/test_frontend.js          # 66 项断言
node portal/tests/test_frontend.js --old    # 还原修复前的写法，复现死循环（5000+ 次请求）
```

覆盖：

1. **会话过期不再刷出无限 logout 请求**。服务重启后本地 token 失效（会话存在服务进程内存里），
   `api()` 收到 401 回调 `logout()`，而 `logout()` 又发一个带旧 token 的登出请求 → 又是 401 →
   无限套娃，把页面和服务器一起拖死（实测线上刷出过 6 万条）。
   修复是「先清本地会话、再发登出请求」+ 重入锁。
2. 刷新后停在原来那一屏（后台留在后台、tab 留在原 tab）。这些界面位置现在也落 localStorage，
   否则一刷新就被打回用户端首页。
3. 非管理角色不会被恢复进后台 —— 换了普通用户登录时，不能因为上一个人停在 admin
   就给他一个空面板。
4. 退出登录会清掉界面位置，不留给下一个人。
5. **SSE 帧解析器**（纯函数，直接喂缓冲）：一块里两帧、跨块的半帧、心跳/注释帧、`event: bye`、
   坏 JSON 不打断后续帧、CRLF。读取循环用 `TextDecoder(..., {stream:true})` —— 测试里故意把
   一个汉字**切在字节中间**喂进去，少了这个参数页面上就会出现 `�`。
6. **实时帧不触发重拉**：进积分 tab 自动建流，收到 2 帧后 `#pt-body` 里出现了这两行
   （含操作人、回滚按钮），而列表接口的请求数始终是 1。
7. **切走 / 登出会 abort 流**（不能只靠服务端心跳发现）；**流回 401 时恰好只请求一次**，
   不重连、不刷 logout；**流反复结束时请求数有界**：1s→2s→4s…封顶 15s 的指数退避，
   测试断言「4 秒内重连次数在 2~5 之间」（实测多为 4；断言卡区间而不是卡具体数字，
   因为它本质上是计时结果）—— 不退避的话这个循环会以 0.4s 一轮跑满上限。
8. **看板 tab 切换同时管住两条数据流的生死**：停在总览时**一条明细、一条实时流都不发**
   （只是打开看板不该给服务端挂一个订阅队列）；切到积分 tab 才拉明细 + 复用看板载荷画趋势图；
   切回总览、以及离开看板去别的分区，流都要 abort。这条是这一版最容易回归的地方 ——
   积分明细从独立菜单页搬进看板内部，判断条件从「分区是不是 points」变成了
   「分区是 dashboard **且** tab 是 points」，三层条件收在一个 `pointsTabVisible()` 里。
9. **趋势图要跟着实时帧一起动，但不许一帧一问**：明细收帧就地插一行是「来一条推一条」，
   趋势是按天聚合 —— 连着来 6 条也只有当天那一格变了。所以走 1.2s 防抖 + 只刷
   `#pt-trend` 那一块，6 帧只触发 1 次 `/api/admin/points/trend`。**趋势数字必须由服务端算**
   （`metrics.daily_points`），前端不许拿帧里的 `points` 往当日柱子上加：回滚行不进口径、
   被回滚掉的原笔也要一起排除，这两条规则只在 `metrics.py` 里有一份，前端自己加一次回滚就对不上了。

│     ├─ admin.py       # 管理后台（含积分明细 / 实时流 / 发放·回滚·校平）

│  ├─ test_search.py      # 分词 / 召回 / 排序 / 索引同步（python -m unittest）
